# 实施与验证计划

状态：全局实施计划；后台账户/RBAC已实施，其余业务能力按本计划继续。身份专项验证与本地提交见user-rbac-implementation.md及review-log.md。

## 1. 定稿与来源纪律

后台账户与完整 RBAC 的本轮方案见[专项设计](user-rbac-design.md)、[施工图](user-rbac-implementation.md)和[单元契约及测试矩阵](user-rbac-units.md)。用户已确认仅后台账户以及令牌严格只存摘要、失败后手动重新发起；不建立身份邮件自动重投任务。以下全局批次与专项 P0—P4 联合实施，不另建平行的内容或身份实现。

先完成设计基线、接口/模块清单、安全基线和参考审计。独立审查者按错误假设审阅，列出契约空白、绕过、并发和生命周期问题；逐条处置后定稿。

Tillgate 的复用单位是业务行为与验收场景，不能以复制文件作为完成标准。每项行为都记录“保留 / 重设计 / 不纳入”及理由；参考系统代码和测试均不能自动成为新系统的正确性依据。

后续只建立新系统的一套实现。没有长期别名、Tillgate 包依赖或“新旧权限字段都接收”的兼容路径。

用户已明确 Collections 和资源管理不能为了前期成本削弱。[完整能力设计](collections-and-assets.md) 是最终功能验收清单，实施批次只决定顺序。数据库按集合配置编译类型化 schema/关系/索引及迁移，不先交付固定 JSONB 引擎再等待用户要求重建；媒体使用同一集合引擎。

## 2. 测试计划先于业务实现

- 单元测试位于各功能同目录 __test__，验证公开规则、状态转换、边界和异常。
- HTTP 集成测试使用 Hono 实例与真实隔离 PostgreSQL schema，覆盖外键、唯一约束、锁、事务和并发。模块私有测试文件不跨模块复用。
- 跨进程旅程分别启动 Bun 开发服务和 Node 生产构建产物，执行相同核心授权与持久化场景。
- 邮件和存储使用可编程测试装置验证真实接缝与失败，不要求默认测试访问第三方账号。
- 新建 Vitest 覆盖率配置时显式列出业务代码匹配范围。初始目标建议 statements/functions/lines 90%、branches 85%，实施前确认配置；不得通过缩小范围或降低门槛换绿。
- 回归测试使用独立期望和可观察结果，不用源码字符串、内部调用次数或复用被测逻辑计算期望。
- 每个确认的源实现缺陷先建立会失败的最小复现场景，再以新系统公开接口验证已消除该症状。
- 集合权限按主体 × operationId × collectionScope 遍历，特别验证同一动态路由下文章权限不能访问页面；scope 不一致绑定和 global 兜底均应失败。
- 生成过程验证确定性、重命名/类型变更数据保留、历史解码及配置/生成物/迁移不匹配拒绝就绪；用真实数据库行为验证 schema，不能只比较生成器自己的快照。
- 每类字段验证配置、校验、SQL 映射、查询、索引、locale、权限和历史恢复；array/blocks 验证顺序/子项身份，关系和展开验证循环、N+1 及预算。
- 媒体版本测试使用不同的真实字节及摘要作为独立期望，验证文件替换、焦点/裁剪、历史读取和引用保护，不能只断言元数据 URL 变了。
- 回收站恢复、永久清除、版本保留和定时发布分别验证外部引用、活跃修订、撤权及进程重启；暂不实现 UI 不影响这些后端验收。

## 3. 最小垂直切片

文件归属按 [代码组织约定](code-organization.md) 执行：进程入口、bootstrap、commands 分开，模块公开业务 API 与 composition 分开，SQL 查询及 __test__ 就近。先补齐该切片实际涉及的 HTTP/模块私有性/schema owner 检查及绕过样本，再合并业务实现；不先创建整棵空业务目录。

先交付应用装配、集合定义归一化、最小可用的 schema 生成/迁移、首个超管初始化、登录、一个业务权限、一个内容集合的草稿创建与发布。第一个集合已经走正式集合编译和查询路径，后续增加字段能力，不另外建立临时固定记录实现。

完整旅程：初始超管 → 配置编辑角色 → 邀请激活 → 编辑者登录 → 创建草稿 → 无发布权时拒绝 → 授予发布权限 → 下一请求成功发布 → 编辑草稿不改变发布快照 → 撤权后拒绝 → 注销后旧令牌拒绝。

切片包含错误响应、requestId、IP/用户限流、大小限制、取消、审计、OpenAPI 和 Node 生产执行。它是首个正式实现批次，审查和四门通过后在该实现上继续扩展。

## 5. 本项目门禁

当前package.json已纳入本期后端及工具，typecheck采用用户确认的bun check；Node API、数据库集成及网络旅程均有实际入口：

- bun run lint：架构依赖约束、类型感知 oxlint、oxfmt 检查；0 警告、0 错误。
- bun run typecheck：所有本阶段工作区、测试和脚本的 TypeScript 检查。
- bun run build：生成 Node 兼容的 API 生产产物。
- bun run test：Vitest 单元与隔离数据库集成测试、覆盖率，以及 Bun/Node 服务冒烟。
- bun run test:e2e：按功能选择跨进程旅程文件执行，不反复全量运行。

OneAster前端UI按[专项施工图](admin-ui-implementation.md)纳入Next生产构建、TSX类型和覆盖率、React行为及开发/生产浏览器冒烟，保留既有后端门禁。真实内容/媒体业务接入仍按对应批次交付。

测试报告分别记录用例数、四项实际覆盖率和匹配范围内的门禁结果；测试依赖不可用时失败并报告，不添加 skip 或空成功。

## 6. 交付与回滚

- 每个批次先检查他人修改，只提交点名文件；规范工具仅按用户明确授权增强 oxlint，不顺带改写已有格式策略或 AGENTS.md。
- 方案变化先更新同批文档，再更新实现和测试。
- 本地Git及origin已明确，当前AGENTS已授权功能完成且四门与审查通过后提交并push。只提交本轮点名文件，Husky与CI按实际四门执行，不宣称远程工作流已运行。
- 一次性发布任务执行 PostgreSQL 迁移和目录投影，实例验证兼容范围，失败不进入 ready；不在监听后异步告警继续服务。滚动期间保留旧实例所需结构，排空后按删除条件清理。
- 初次上线不涉及源系统数据切换。新部署可以回退到本批次前的产物；数据库变更不得破坏仍运行版本，删除性迁移和备份恢复需单独说明。
- 部署、证书/入口变更及实际发布仍需用户单独授权。
