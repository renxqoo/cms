## 2. 已做行为探针

以下探针用 Bun 直接导入源函数，注入最小内存依赖，不连接源数据库，不运行源系统服务。它们验证特定函数行为，不等同于已证明线上攻击链。

### 2.1 接口匹配依赖行顺序

位置：apps/admin-api/src/http/middleware/acl.ts 的 matchBinding。

输入顺序：GET /v1/files/:id → files:read；GET /v1/files/export → files:export。

对 GET /v1/files/export，函数返回第一条参数路由对应 files:read；交换行顺序后返回 files:export。相同请求和规则集合得到不同鉴权结果，表明自建匹配器与真实路由选择可能漂移。

新系统：运行时使用 Hono 已匹配操作的 operationId，不复制这段匹配算法。回归场景验证静态/参数路径、HEAD 和不同注册顺序下的实际 HTTP 授权结果。

### 2.2 分组可以挂在分组下

位置：packages/control-plane/src/application/rbac/create-permission.ts。

输入 type=group、parentId 指向一个 group。最小仓储确认该父节点存在，源函数接受并写入 parentId=1，与“group 顶层”的声明规则不符。

新系统：展示节点类型与父节点类型采用封闭规则；分组必须顶层。修改类型时一并检查现有子节点，数据库约束与应用校验共同守护。

### 2.3 自定义页面可以没有权限码

位置：同一 create-permission 函数。

输入 type=page、parentId 指向 group、code=null，源函数接受。该结果与文件中“custom page 必须有码”的声明冲突。此探针证明校验缺口，不据此声称所有无编码页面都造成数据越权。

新系统：菜单可以显式声明“仅认证可见”或引用 permissionId，不能用 null 的隐含语义代替访问策略；菜单本身不授予接口访问权。

## 3. 静态核对到的风险和设计差异

以下尚未构造完整 HTTP/数据库复现，不能当作已证实的线上漏洞；纳入新系统的审查与回归计划。

- HEAD：源契约允许独立 HEAD 绑定，ACL 却先将 HEAD 归一成 GET；独立 HEAD 配置可能永不命中。新契约不提供矛盾的独立配置。
- code 身份：源权限更新可改变 code/type/source，而角色授权通过 permissionId 跟随节点变化；展示调整与授权语义耦合。新设计固定权限身份，显示信息单独维护。
- 接口绑定：源创建绑定仅验证权限记录存在，未要求它具有有效 code；绑定到无码分组可能落成无法使用的接口。新系统只能绑定有效权限身份。
- 启动：verifyRbacStartup 异步执行且数据库不可达时仅告警，可能先开始监听。新系统在必要迁移与权限目录核对通过前不进入 ready 状态。
- 并发与审计：角色授权差异在事务前读取，审计在业务写入后另行追加；并发操作或审计失败时，事实与审计可能失配。新系统同事务读取/更新/审计，并校验版本。
- UI 测试：rbac-button-gating.test.ts 通过源码字符串判断按钮权限，不能证明运行中的按钮或 HTTP 授权正确。新系统以公开接口行为与越权矩阵为依据。
- 开发假身份：源 get-admin.ts 有 DEV_FAKE_ME 分支。本项目不引入可切换成全权限身份的业务运行路径。
